## Key Code
- Plain `commit -m`: `write_locked_index(..., COMMIT_LOCK | SKIP_IF_UNCHANGED)` then `commit_style = COMMIT_AS_IS; ret = repo_get_index_file(...)` (commit.c:481-494). Initial refresh may write index metadata; **no real index.lock is retained across hooks**.
- `commit -a`/`--include` with paths: `write_locked_index(..., 0)` then `COMMIT_NORMAL`, hooks receive `get_lock_file_path(&index_lock)` (commit.c:452-469). Here the real index.lock persists through hooks, tree/commit creation and ref publication; refusal rolls it back. This is not the requested plain staged commit, and `-a` would change staging semantics.
- `run_commit_hook`: `GIT_INDEX_FILE=<index_file>` (commit.c:1954). For plain commits this is `.git/index` in the fixture; for `-a` it is the absolute `.git/index.lock`. Hook `git add` inherits this and locks `<GIT_INDEX_FILE>.lock`—the latter means index.lock.lock, not the protected original index.
- `prepare_to_commit` rereads the index after pre-commit, calls `cache_tree_update`, **then** runs prepare-commit-msg and commit-msg (builtin/commit.c:1096-1135). `commit_tree_extended` later uses `the_repository->index->cache_tree->oid` (1926-1931), not a new post-commit-msg disk-index read.
- `COMMIT_AS_IS` rollback/install do nothing (217-251). `COMMIT_NORMAL` rollback removes the pending lock-file index; success installs it after the ref update. Post-commit runs after this (1945-1956).

## Architecture / Wrapper Assessment
1. Preserve original pre-commit, prepare-commit-msg, commit-msg and post-commit, plus **reference-transaction** and any other invoked original hooks; hooksPath replaces the entire lookup directory, not merely commit-msg. Resolve the original effective hook locations before overriding them, including relative-path/worktree semantics and executable eligibility. Preserve argv, stdin, cwd, environment, message edits and exit status; no double execution or treating an original refusal as success.
2. Appending validation after successful original commit-msg preserves that refusal, but validates a mutable on-disk index **after Git already selected an in-memory tree**. Prepare-commit-msg/commit-msg may edit the index; those edits need not enter this commit. Current-index equality alone does not establish which earlier tree Git selected (e.g. an index changed before tree capture and restored before validation).
3. Ordinary commit-msg validation does not hold index.lock, so cooperating Git writers can change the same path after its check. Acquiring and releasing index.lock only inside that hook closes the read's own race, not the interval through publication. Leaving a lock behind with a separate lifetime/cleanup protocol is a different transaction design, not a normal forwarding wrapper. Native Git does not adopt such a hook-owned lock in COMMIT_AS_IS.
4. A later original reference-transaction prepared hook can still modify the actual index or refuse publication. It must retain its stdin stream and phase semantics; committed/post-commit status cannot roll back a published commit. Holding a real index lock across such hooks can newly break originals that stage files; this is a lifecycle compatibility constraint, not merely a dispatch problem. Post-commit index edits are post-publication intent, not evidence of the committed tree.
5. A prepared reference-transaction hook sees the proposed immutable commit OID on stdin; inspecting its tree is a **different possible investigation seam**, not proof that commit-msg validates that tree, nor a complete lock/preservation protocol. Must distinguish HEAD-affecting updates from unrelated/nested transactions, retain original hook behavior and establish expected parent/index semantics. Not approved or implemented here.
6. Normal plain-hook refusal preserves hook index changes, which is desirable for uncertain intent; changing to `-a`, partial/private commit styles or restoring an earlier index can instead discard them. A design must explicitly preserve competing/unattributed deltas on every refusal, including original-hook and ref-hook failures. Do not “repair” by overwriting the real index with the captured snapshot.
7. Command-local hooksPath propagates via Git configuration environment to nested Git processes. Forwarding must avoid recursive dispatch and unintended loss/change of original nested-hook lookup semantics. `--no-verify` skips commit-msg/pre-commit, so it cannot be permitted to bypass a required validator. Crash/timeouts, external lock ownership and noncooperative direct index replacement remain separate risks.

## Private-Index Staging: Separate Provenance Boundary
Yes, private-index staging **can remove the read-after-real-git-add attribution gap**, if implemented as an actual isolated transaction: stage explicit leaves into an exclusively controlled private index initialized from a known snapshot; read resulting exact mode/OID/absence identities there, where unrelated writers cannot replace them. This proves which blobs that staging operation produced, not that they are policy-approved or reflect an immutable worktree instant; filters and concurrent worktree edits still need explicit semantics.
Then acquire the real index lock, reread and compare against the captured baseline/HEAD (or rigorously account for every admitted concurrent delta), and conditionally install only the proven candidate. On mismatch, defer without modifying the actual index or losing competing intent. Handle deletions, modes, unmerged entries, gitlinks, split/sparse-index dependencies, SHA width and byte paths; never grant directory-prefix authority. Release-to-native-commit still leaves the later commit boundary unresolved unless an additional proven transaction closes it. **A hooksPath wrapper alone never proves new-staging provenance.**
