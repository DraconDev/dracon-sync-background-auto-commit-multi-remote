## Specific Integration: Small, Viable Pieces
- Add internal `StagedIntentSnapshot { head, entries }` with exact byte-path keys and stage-0 `(mode, oid)` identities. Represent cached deletion as explicit absence relative to captured HEAD; name+OID alone cannot represent a deletion. Reject unmerged stages rather than converting them to consent. Preserve full OID width; do not hardcode SHA-1.
- Capture at sync cycle entry BEFORE standard-file staging, pull/merge, cleanup and preparation, not inside `stage_commit_and_push` after classification. Those earlier phases can mutate index/HEAD (`sync.rs:5734-5784`). If they change the captured parent/index, either prove their exact owned delta or defer/restart with a new bounded epoch; do not silently recapture arbitrary concurrent content as same-cycle intent.
- Replace `_status` at `stage_commit_and_push:4248` with a reference to explicit intent/proof context (or add it); RepoStatus counts cannot supply identity or staged-vs-unstaged provenance. Thread snapshot independently of filtered `entries` so net `diff HEAD` pruning cannot delete it.
- Keep two sets: eligible **already-staged identities** and **worktree paths to stage**. Evaluate already-staged eligibility against cached blob sizes plus existing policies/private suppression, not current worktree size/content. Do not automatically authorize private materializations or paths rejected by hooks.
- Exclude initial staged identities from EVERY daemon re-add path, not just the final list: ordinary/force staging, standard-file staging, gitlink updates and missing-file removal. A partially staged path must commit its cached blob while its later worktree edits/deletion remain untouched. Rename should be treated as tree-entry deletion/addition, not pathname similarity.
- Merge eligible initial cached changes into the commit-decision condition even when `to_stage` is empty; current `if !to_stage.is_empty()` caller gate otherwise skips staged-only intent. Do not change filter-only behavior for worktree-only smudge noise.
- Replace directory-prefix consent in `staged_extra_paths` with exact admitted leaf identities. `stage_existing_files_suppressing` already has expanded leaf paths at `1504-1511`, but returns `Result<()>`; it must return explicit staging evidence, not grant consent to arbitrary future children. Gitlinks remain single nonrecursive entries.
- Final validator compares the complete changed index set against authorized exact identities, including deletions, and checks initial staged identities stayed unchanged. New extras, replaced OIDs/modes at an existing name, and removed intent entries defer with observed index/worktree retained. A pathname match is insufficient.
- Minimal guarded-first slice: when eligible cycle-entry staged intent exists, do a staged-only pass (no worktree re-add), verify exact identities, run hooks, then validate/seal under lock. This preserves partial staging without requiring provenance attribution for newly staged blobs. Not applicable as a private-materialization waiver; manifest preparation that cannot coexist safely must defer.

## Existing Seal Reuse and Missing Atomic Boundary
- `prepare_storage_commit_inner` (`storage/mod.rs:2754-2797`) acquires CommitLock, opens the actual index, verifies storage entries, writes an immutable tree, creates an unreferenced commit and returns lock+commit+previous tip. `advance_sealed_commit` (`sync.rs:5218-5236`) uses native update-ref with expected old tip, retaining reference-transaction hooks.
- Extend the guarded prepare API to receive expected HEAD and exact index intent; compare **after acquiring lock and loading the fresh index, before write_tree_to/commit**. Current API accepts only repo/message and has NO cycle-intent or post-hook identity check. It seals whatever storage-valid index exists after hooks.
- `run_sealed_commit_hooks:5299-5334` runs pre-commit, prepare-commit-msg and commit-msg before acquiring CommitLock; hooks may change index as well as message. Require post-hook identity equality, not merely successful exit. Re-run index-sensitive policy/size/private/forward-only checks against the same locked tree (or a verified identical tree), since current checks precede hooks (`4557-4579`).
- Hold lock through expected-old-tip ref publication. Preserve current full lifecycle and edited/empty-message handling; post-commit runs only after success. Also require expected cycle HEAD at seal time, not just seal-time parent CAS: current parent is read late at `2776-2780`.
- Cooperative Git index locking cannot prevent arbitrary direct filesystem index replacement; ownership/identity checks should detect changed lock/index before publication where possible, but no claim of adversarial filesystem exclusion is justified.

## Hard API Constraints / Larger Work (Not a Tiny Patch)
- Native `commit_staged_owned:5206-5213` is simply `git commit -m`: no expected-tree/OID argument, no daemon callback between native hooks and commit. Checking before invoking it leaves an index race; holding real index.lock while invoking it blocks Git itself. Running hooks twice is not a fix.
- A complete native-path solution needs a reviewed generic immutable-commit transaction preserving native hook/ref semantics (or equivalent integration), not a pretend atomic last-moment comparison. Existing manual lifecycle is a reuse candidate, not proof of parity for every Git feature.
- Storage CommitLock requires an enrolled, locally matching SHA256 repo ID (`storage_core/index.rs:39-50`). Never fabricate enrollment/IDs to reuse it for ordinary repositories. Generic IndexLock exists but its Drop unconditionally unlinks by pathname (`git/status.rs:75-79`); harden ownership before using it as durable commit lock. Storage lock has inode-checked Drop and crash recovery tests.
- Newly staged provenance has another race: native `git add` releases its lock before the daemon can read resulting OIDs (`sync.rs:1587`). A read-after-add can accidentally bless another writer's same-path replacement. Exact leaf names alone do not close this. Full solution may need private-index staging plus compare-and-publish transaction under real lock; this is larger design, not existing `IndexTransaction` drop-in.
- Existing storage `IndexSnapshot` is an opaque fingerprint tied to operator-bound `IndexTransaction`/StageBundle and metadata publication (`storage_core/index.rs:127-209,215-245`), not a general-purpose staged map or native commit API. Reuse its transaction principles, not its authority assumptions.

## Batching: Explicit Decision Required
- `cap_batch_union:4226-4242` caps selected regular/gitlink staging candidates; cached changes already in the real index are NOT capped. Extras guard receives original uncapped `to_stage` (`4447`); native/sealed commit consumes entire index. Therefore 120 pre-staged eligible identities can already commit despite effective stage limit 100.
- Current source default is 100000 (`policy.rs:1262-1267`), not 100; parent's 100 must be an effective configuration/fixture assumption. Documentation nevertheless promises each batch <= configured limit (`575-578`). This is a real semantics conflict, not authority to silently split/unstage operator intent.
- Minimal non-destructive option: explicitly retain all authorized pre-staged entries, admit no new work when their count exhausts the batch budget, and document/test a pre-staged exception. Requires policy approval because strict <=100 is then false for 120 already staged.
- If strict total-commit cap is mandatory, defer with explicit diagnostic until a subset-commit transaction preserving residual staged entries is designed. Never reset the extra 20, bless them by directory prefix, or claim ordinary cap_batch_union alone solves it.
