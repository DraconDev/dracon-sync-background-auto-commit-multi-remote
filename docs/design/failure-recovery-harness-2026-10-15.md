# Integrated disposable failure/recovery harness — 2026-10-15

## Run one bounded command

From the utilities workspace:

```sh
bash dracon-sync/scripts/verify-failure-recovery.sh
```

From this checkout: `bash scripts/verify-failure-recovery.sh`.

Requires Linux, Git, Node, Cargo, GNU timeout, and an existing configured Git
commit identity. No identity is invented or changed. The wrapper selects the
exact one scenario and refuses a zero-test success. Cargo has a 300-second
TERM / additional 10-second KILL deadline; the episode has an independent
60-second Tokio deadline. Compilation is included in the wrapper budget.
Nothing starts a daemon, changes a service, loads fleet credentials, or contacts
real shared storage. All repositories and bare remotes are newly created under
`/tmp/dracon-failure-recovery-*`; fixture-local hooks do not modify global Git
settings or install hooks into any existing checkout.

## Scenario and concrete contract mapping

`src/daemon/failure_recovery_tests.rs` is included below the real discovery
scheduler so it can use its private test seam without widening production APIs.
This is one overlapping multi-repository episode, not four old tests wrapped in
a shell script. It invokes production discovery, inspection, recovery admission,
scoped resource ownership, push retries, bucket preparation, staging and commit.

| Requirement | Assertion in the integrated episode |
| --- | --- |
| Slow discovery | Establish a real four-repository discovery snapshot, then gate a refresh before the same real tree walker. Poll it 200 times during other faults; the last matching complete snapshot stays usable, exactly one walk starts, and no duplicate walker runs |
| Hung required filter | An equal-size tracked mutation enters a required clean filter with a TERM-resistant child. Atomic PID markers establish readiness. Actual inspection remains unfinished while healthy repositories progress |
| Failing hook | An actual pre-push waits at a barrier while the other faults coexist, then refuses the push. A configured three-attempt production retry budget executes the permanent local refusal exactly once; the bare ref stays unchanged |
| Simulated bucket outage | A deterministic local storage adapter refuses two upload attempts through actual `sync_repo` bucket preparation. HEAD, bare ref, manifest, regenerated bytes and empty object store are checked before recovery |
| Healthy-repo progress | With local capacity one and a hook occupying the separate push lane, the healthy repo completes real inspection and two whole `sync_repo` commit cycles. Both HEAD and committed bytes advance while discovery/filter/hook remain unfinished. Publication intentionally queues behind the single-flight push lane and succeeds after release |
| Fail-closed publication | Filter and bucket repos retain their original local and remote heads while blocked. Hook rejection cannot change the remote ref. No object or reference is fabricated during storage refusal |
| Bounded retries | Actual `apply_outcome(Blocked)` installs the production 300-second stage cooldown; `stage_cooldown_remaining` refuses 100 immediate readmissions per outage attempt while actual upload subprocess invocations are counted. Only its explicit `Instant` inputs advance. `SyncRecovery` separately gates genuine cancelled-worker recovery. The hook's retry loop independently fails fast within its configured budget |
| Cleanup | Scheduler expiration produces one cancellation request, never a duplicate. The inspection owner is aborted and its typed cancellation awaited before recovery finishes. The recorded filter/helper and hook/helper identities are absent or stopped in `/proc`; returned local capacity is checked |
| Recovery | Remove only fixture fault markers, release and join the sole discovery walk, reinspect and sync failed repos, publish all refs, check verified object bytes against the committed manifest, and retain the old raw asset blob in Git. A repeated bucket pass makes no duplicate commit |

The storage boundary is deliberately simulated by a tiny Node adapter importing
only `node:fs` and `node:crypto`, writing content-addressed bytes inside the
fixture's `.git/simulated-store`. The daemon's configuration validation,
upload-bound digest check, materialization exclusion, final staged-reference
verification and commit remain production code. Synthetic credential locations
are inside TempDir and never read. This does NOT qualify OVH availability,
network retry behavior, real credentials or S3 durability.

The injected slow walk uses `Discovery::poll_with`; only its readiness barrier
is fake, and the closure calls the same real repository walker after release.
The test moves the private scan deadline to request a refresh without waiting
30 seconds. Stage-cooldown and `SyncRecovery` checks use logical `Instant`
arguments already provided by their production interfaces; no retry policy is
relaxed and no production timing configuration changes. A bucket `Blocked`
result is deliberately NOT misrepresented as a worker error to manufacture
error-backoff evidence; its actual outcome handler and stage cooldown are used.
Only the Blocked outcome handler is invoked; success-ledger writers are not
called against any fleet state.

Every spawned async task has an abort-on-drop owner. A separate release guard
unblocks the non-cancellable blocking walk even on assertion failure; its channel
also has a finite receive deadline. Normal success joins all work. PID markers
publish via temporary file plus rename rather than treating an empty file as a
completed readiness handshake. No arbitrary process is killed by PID or name;
production owned Git process-group guards perform cancellation cleanup.

## Defect found by integration

The first realistic commit cycle exposed unconditional post-commit remote
alternate-default deletion. `prune_other_default_branch` attempted to delete
`master` after every `main` commit even when no remote `master` was observed.
That unnecessary push queued behind the intentionally blocked hook and kept
an otherwise successful sync future from returning.

`src/git/branch.rs` now requests this remote deletion only if the alternate
exists in the remote-tracking snapshot. A later fetch can expose new alternates
for a subsequent pass; cleanup is conservative rather than deleting unobserved
remote branches. The integrated episode additionally proves:

1. An absent alternate causes zero push-hook invocations.
2. An observed alternate still requests deletion and honors a rejecting hook,
   leaving the remote branch intact.
3. Clearing that rejection deletes only the alternate and preserves `main`.

The existing narrow maintenance rewrite exception is unchanged. There is no new
hook bypass, force push, history rewrite, lock removal or fleet config change.
